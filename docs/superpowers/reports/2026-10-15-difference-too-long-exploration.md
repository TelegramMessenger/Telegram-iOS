Raw findings of five read-only researchers (workflow wf_878b0d78-13a), kept as input for the brainstorming of
correct differenceTooLong handling (owner request, 2026-10-15). Anchors are at the commits each section names.

## channel-revalidation: How channels are revalidated today (ChannelState.invalidatedPts + ChannelMessageStateVersionAttribute + HistoryViewStateValidation), end to end, and what of it carries over to regular chats after a differenceTooLong

All anchors are at HEAD 69939c45c0. I read AccountStateManager.swift, ResetState.swift, StateReplay.swift, SyncResolve.swift, ChannelPolling.swift, HistoryViewStateValidation.swift (HVSV), AccountViewTracker.swift and Holes.swift with `git show HEAD:`. The audit doc's anchors refer to 171825ce49 and use the old file names, so don't mix the two sets.

1) The model. A channel has `ChannelState{pts, invalidatedPts?, synchronizedUntilMessageId?}` (SyncCore_ChannelState.swift:3-60), and a channel message can carry `ChannelMessageStateVersionAttribute(pts)` (SyncCore_ChannelMessageStateVersionAttribute.swift). A stored Cloud message of the channel counts as valid only if it has the attribute and its pts is >= invalidatedPts. A message without the attribute counts as invalid (HVSV:45-74). Nothing ever sets invalidatedPts back to nil on an existing state, so once a channel has been invalidated the check stays on for good. The scheme therefore depends on pts only ever growing, and on every channel ingress stamping the attribute. These places stamp it:
- ChannelPolling.swift:239, 382, 433, 555
- UpdateInterpreter.swift:234, 347
- SyncResolve.swift:981
- Holes.swift:1037 (hole fill, using channelMessages.pts)
- FetchChatList.swift:182
- ApplyUpdateMessage.swift:362-367
- ChatListFiltering.swift
- the validator itself

One ingress doesn't stamp: reply targets fetched by resolveAssociatedMessages (SyncResolve.swift:744-800). Each such message costs one validation the first time it is shown.

2) Who writes invalidatedPts.
- (a) `resetChannels` (ChannelPolling.swift:122-325) calls messages.getPeerDialogs. It then sets invalidatedPts := dialog.pts (217, 287) and pts := dialog.pts, and stores the stamped top message. It resets read state and tag summaries and resets forum topic lists. It also adds a "hole from previous state" from synchronizedUntilMessageId+1 (or the top stored id+1) up to the new top-1, plus a pinned-tag hole (StateReplay.swift:398-415, 1986-2000).
  - It runs for every channel the server reports with `updateChannelTooLong` inside a getDifference. The path is UpdateInterpreter.swift:172-180 → channelsToPoll, then `shouldResetChannels: true` from SyncDifference.swift:82 → UpdateInterpreter.swift:1298-1327.
  - There is also an async variant, AccountStateManager.swift:607-680, which persists `AuthorizedAccountState.invalidatedChannels`.
  - So channel invalidation plus lazy validation runs routinely in production.
- (b) `channelDifferenceTooLong` in pollChannel (ChannelPolling.swift:512-560) does the same, using the dialog embedded in the reply.
- (c) The replay coalesces `.UpdateChannelInvalidationPts` (StateReplay.swift:150-151, 197-198) and applies it (1181-1185).

It is NOT written by:
- the common `_internal_resetAccountState`. ResetState.swift:117-123 only calls `withUpdatedPts`; channels there get the full-range hole instead.
- fetchChatListHole (Holes.swift:1371-1377), which does the same.
- resolveMissingPeerChatInfos. SyncResolve.swift:957 builds a local `ChannelState(invalidatedPts: pts)` only to stamp messages and never stores it.

Two dead pieces:
- `HoleFromPreviousState.validateChannelPts` (AccountIntermediateState.swift:164-177) is carried and merged but never read: the replay iterates `for (namespace, _)` at StateReplay.swift:399.
- `RegularChatState(invalidatedPts:)` (SyncCore_RegularChatState.swift) is persisted under key "ipts" and registered (AccountManager.swift:103). It is read only at SyncSnapshot.swift:393, with the assignment commented out, and nothing ever writes it. Someone started this generalization and left it unfinished.

3) What drives validation.
- AccountViewTracker calls `HistoryViewStateValidationContexts.updateView` only for `.peer`/`.thread` locations of a CloudChannel (AccountViewTracker.swift:1983-2008).
- `wrappedHistoryViewAdditionalData` adds `.peerChatState` only for CloudChannel (190-210). That entry is the only source of HistoryState (HVSV:153-160).
- Only the view tracker's aroundMessageOfInterest / aroundId / aroundMessage entry points pass through this. Direct Postbox views are never validated: SparseMessageList.swift:202 (top items) and ChatHistoryPreloadManager.

`updateView` (HVSV:122-378):
- It skips custom tags, anchor-only loading views (137), and every tag except nil, unseenPersonalMessage, unseenReaction, unseenPollVote, music and pinned (146).
- It walks every entry of the view. That is the loaded window (`historyMessageCount = 44`, ChatHistoryListNode.swift:49), not just the rows on screen.
- It keeps only Cloud messages of the view's own peer.
- It splits the invalid messages into contiguous runs, broken wherever a valid message sits between them.
- It skips ids already in flight (`batchReferences`, kept per view id), cuts runs into 64-id batches (90), and starts one request per batch.
- Thread views (location.threadId set, 163-269) go through validateReplyThreadMessagesBatch instead.

4) The request and how the result is applied.
- The request is `messages.getHistory(peer, offset_id=last+1, add_offset=0, limit=n, max_id=last+1, min_id=first-1, hash)` (HVSV:560).
- `hash` comes from `hashForMessages`: the stored batch, sorted by MessageIndex descending, hashing the id, the edit date (or date) and a 1 when pinned (474-500).
- Tagged views use getUnreadMentions / getUnreadReactions / getUnreadPollVotes, which take no hash, or messages.search(filter, hash) (546-555).

validateBatch (781-1033) then does this:
- `messagesNotModified`: every batch message is restamped with the channelState.pts captured when the view emitted (1002-1031).
- Otherwise each returned message is stamped with channelMessages.pts.
  - If its edit date differs from the batch snapshot (`previous[id]`, not the current row, 876), it is replaced wholesale (896-901).
  - Otherwise only its stamp is replaced.
- A returned id the client doesn't have is inserted (927).
- Batch ids missing from the reply are checked with channels.getMessages (827). Those still missing, messageEmpty included:
  - are deleted with `_internal_deleteMessages` (995) in an untagged view;
  - lose the tag and are restamped (967-991) in a tagged view.
- In tagged views every id that wasn't returned loses the tag (932-962).
- If the confirmation request itself fails, every missing id is treated as deleted (859).
- The `default:` branch (864) deletes missing ids with no confirmation for any non-channel HistoryState. A new `.regular` case would fall into it.

Threads use getReplies (634). A `notModified` reply there does nothing (1184-1185), and the release of the thread's batch references is commented out (249-255). So a thread is revalidated on every open but never loops within one view.

"Validated" exists only as the stamp. There is no range record and no epoch.

5) Cost. Each view emission costs one hashed getHistory per contiguous run of up to 64 unvalidated messages:
- about 1 request when a chat is opened;
- about 1 more per scroll page that brings unvalidated messages into the 44-message window;
- plus 1 channels.getMessages for any batch that has missing ids.

Each message is validated once per invalidation epoch. Every validated message is rewritten (restamped), which redraws it. There is no throttle, no backoff and no global cap, and views open at the same time (chat, pinned bar, mention navigation) validate independently.

Two failure modes, both derived from reading and not reproduced:
- A request error completes the batch without stamping, and the next emission asks again with no backoff.
- A message the server still has but getHistory doesn't return is never stamped. This happens when it falls outside (min_id, max_id) or past `limit`; one case is imported history, because runs are ordered by MessageIndex (timestamp first, Message.swift:236-250) while min/max are ids. Postbox `updateMessage` emits even no-op rewrites (MessageHistoryTable.swift:575-579), so each completion re-triggers the view and another round starts while the view stays open.

6) What validation never reaches:
- shared-media tabs other than music: photo/video, files, links, voice, GIF;
- the gallery;
- SparseMessageList grids;
- custom-tag views;
- local search results;
- reply and quote previews, and anything else rendered by message id;
- notifications;
- a migrated basic group's messages shown inside a supergroup view;
- monoforum threads, where the thread path passes `Int32(clamping: threadId)` as a getReplies msgId.

The chat list's top message is right only because a reset re-stores it. Stale messages above the new top stay until the chat is opened: see "TODO: delete messages later than top" at ChannelPolling.swift:320.

EarliestUnseenPersonalMentionMessage.swift:21-50 reads invalidatedPts with the opposite convention: there, a message without the stamp counts as valid.

7) What the common reset does to regular chats today.
- ResetState.swift:18-24 adds a 1…Int32.max-1 `.everywhere` hole for every chat-list peer, channels included. An `.everywhere` hole also covers the tag spaces (MessageHistoryHoleIndexTable.swift:323-338).
- Storing each fetched top message with `.UpperHistoryBlock` removes the hole from that id upward (Postbox.swift:2204-2219).
- Holes hide the stored entries under them (MessageHistoryViewState.swift sampleHoleRanges, 655+). So a chat opens showing only the top message, and the view loads below it by filling the hole.
- A fill's `addMessages` overwrites existing ids (MessageHistoryIndexTable.swift:99-105 → `.InsertExistingMessage` → `justUpdate`), so edits inside filled ranges do heal.
- Nothing in fetchMessageHistoryHole deletes stored messages that the server didn't return inside `filledRange` (Holes.swift:1074-1186). So messages deleted during the gap reappear once the fill completes.
- Stored messages newer than the new top sit outside every hole. They are visible immediately and become the chat's top index.

So "edits stay stale" is only true outside filled ranges: reply previews, search, pages not yet viewed. Inside filled ranges the defect is deletion, plus the cost of unhashed refetches and nothing being readable offline until the fill arrives. Channels caught by the common reset have the same problem. Their pts jumps to the dialog's pts (ResetState.swift:117-123) without invalidatedPts being raised, so the skipped channel updates never switch on the validation they already have.

8) What carries over to regular chats and what doesn't.

Carries over:
- the view-driven lazy driver;
- runs, batching and in-flight dedup;
- hashed getHistory with min/max bounds (it accepts any InputPeer);
- the diff-and-apply step;
- the tag variants;
- a persisted per-peer marker (RegularChatState already exists).

Specific to channels:
- (1) The stamp value. channelMessages carries `pts:int`; messages.messages and messagesSlice, which user and basic-group chats return, carry none (swift_scheme.tl:293-295). A regular stamp would have to be the client's common pts at request start, or a reset generation counter.
- (2) Granularity. updates.differenceTooLong carries only pts (scheme:501), and `dialog.pts` is flag-gated, so one value has to invalidate every user and basic-group chat at once.
- (3) Confirming deletions. channels.getMessages is channel-only. Regular chats need messages.getMessages(id:), since their ids are global to the account; SyncResolve.swift:759-796 already branches this way.
- (4) No regular-chat ingress stamps anything today.
- (5) The CloudChannel-only gates: AccountViewTracker 190-210 and 1983-2008, and HistoryState.
- (6) The thread path (getReplies) doesn't fit Saved Messages sub-chats (getSavedHistory) or bot forums.

Other clients, read from copies of each project's master fetched into the shared scratch directory on 2026-10-15:
- Android (DrKLO/Telegram) sends `pts_total_limit` 5000 (Wi-Fi) or 1000 on the first sync (MessagesController.getDifference). On differenceTooLong it wipes stored messages, media and holes for every non-secret dialog (MessagesStorage.resetDialogs). On channelDifferenceTooLong it does the same for the one channel (MessagesStorage.overwriteChannel).
- tdlib: differenceTooLong is a `// TODO` that sets pts and re-polls (UpdatesManager::on_get_difference). Its channel gap handling is a comment listing four strategies, followed by a reset of the database ranges (MessagesManager::on_get_channel_dialog).
- tdesktop logs "updates.differenceTooLong is not supported" (api_updates.cpp).
- Neither tdlib nor tdesktop sends a non-zero getHistory hash. How the server handles a hashed getHistory for a non-channel peer is untested by any public client.

### Design implications

- The channel template exists and runs in production on every difference-driven channel reset. Applying it to regular chats means: write an invalidation marker at the common reset, widen two gates (AccountViewTracker.swift:190-210 and 1983-2008, plus HistoryState in HVSV), and add a `.regular` request/confirm path. The reuse is real, but every channel-specific assumption listed here has to be re-decided.
- The persisted marker can be per peer or one value for the account. Per peer: RegularChatState(invalidatedPts:) is already declared, encoded and registered, and it plugs into the existing `.peerChatState` additionalData. The cost is N writes at reset, plus deciding what a chat that is not in the chat list yet should get. Account-level: one write at reset, but it needs new plumbing into the view (another additionalData entry, or reading AuthorizedAccountState).
- Stamp value: regular replies carry no pts, so the stamp must be the client's common pts captured at request start (valid because pts only grows and a later reset raises the threshold), or a reset generation counter. A generation counter avoids mixing pts domains when ChannelMessageStateVersionAttribute is reused for non-channel peers.
- Stamping cost: the scheme treats unstamped messages as invalid. Every regular ingress path would need to stamp: SyncDifference new messages, updateNewMessage/updateEditMessage, hole fill, FetchChatList, ApplyUpdateMessage send results, getMessages resolution. The alternative is to accept one hashed (usually notModified) validation per unstamped post-reset message the first time it is shown. A third option avoids most stamping: regular-chat ids are allocated from one ascending per-account sequence, so a message whose id is above the account's top id at reset time cannot predate the reset. 'Suspect' could then mean id <= thresholdId and no fresh stamp. The threshold must come from something reliable, and imported-history ids need handling.
- Choose lazy (channel-style) or hole-based recovery for regular chats; do not stack both naively. Today the reset adds a full-range hole, so the first open costs an unhashed fill and then, if validation is added, a second hashed request for the same messages, unless fills stamp too. The channel-style alternative is a gap hole above the stored top (setNeedsHoleFromPreviousState already works for any peer) and keeping older messages visible while they validate.
- Deleted-during-gap messages: a hole-based design needs the fill to delete stored messages the server did not return inside the strict filled range. That is a Postbox/Holes change, and with tag spaces it is only sound for `.everywhere` fills. A validation-based design gets deletion from getMessages confirmation. Either way, stored messages above the new top need handling: resetChannels has the same unfixed TODO at ChannelPolling.swift:320, and after a reset those messages are both visible and the chat-list top.
- Deletion confirmation for regular chats must use messages.getMessages(id:), since ids are global to the account; SyncResolve.swift:759-796 already shows the branch. Do not inherit two current behaviours: deleting everything when the confirm request fails (HVSV:859), and the `default:` branch that deletes without confirming (HVSV:864). A FLOOD_WAIT or network error must not delete user messages.
- Fix the in-flight race before reusing the apply step. Compare against the row in the apply transaction rather than `previous[id]`, and keep the newer edit. Skip deleting ids that were re-stored after the batch began; Holes.swift's StoredVersions/stableVersion pattern does this. Regular chats receive edits and deletes through the common box at the same time as validation runs.
- Avoid the restamp loop. Stamp a message once its existence is confirmed even when getHistory did not return it. Build min_id/max_id from the min and max ids in the run, not its first and last entries in timestamp order (imported history). Add backoff or a per-peer cooldown after an error, as the scheduled/quick-reply validators already have (60 s, HVSV:379-428).
- Coverage gaps carry over unless addressed: shared-media tabs other than music, the gallery, SparseMessageList, custom-tag (Saved Messages tag) views, local search, reply/quote previews and getMessage-by-id rendering, notifications. For regular chats, Saved Messages sub-chats (getSavedHistory) and bot forums need their own request instead of getReplies. Decide which of these the fix must cover; the channel scheme leaves them stale too.
- The same reset leaves channels exposed. Raising invalidatedPts for each channel in ResetState.swift:117-123 (and in fetchChatListHole when pts actually jumps) would turn on their existing validation. Today the reset skips channel updates silently.
- Request budget per opened regular chat after a reset, mirroring channels: about 1 hashed getHistory on open, about 1 per scrolled page of unvalidated messages, and 1 messages.getMessages per batch with missing ids, with no global cap. A reset invalidates every regular chat at once, so the budget scales with how many chats the user opens, not how many changed.
- Testability: HistoryViewStateValidationContexts is internal and constructible from (queue, postbox, network, accountPeerId). The StateSync harness (ScriptedServer + real Network + Postbox) can drive it with scripted getHistory/getMessages replies. Today nothing tests the validator.

### Open questions

- Server: for a user or basic-group peer, does messages.getHistory honour a non-zero `hash` with the same formula the iOS channel validator uses (id, edit_date or date, pinned bit, in id-descending order), scoped to the min_id/max_id/limit slice, and return messages.messagesNotModified? No public client (tdlib, tdesktop) sends a non-zero getHistory hash, so this cannot be checked from client code.
- Server: does the getHistory hash (or edit_date) change on reactions, view counts, reply counters or media/webpage refreshes? If not, edits that don't bump edit_date are invisible to hash validation.
- Server: for regular chats, does messages.getMessages return messageEmpty for ids deleted during the gap (including 'delete for me' and history clears), so a missing result can be read as deleted?
- Owner: after a common differenceTooLong, should regular chats keep showing their stored messages while they validate lazily (the channel model, with a gap hole above the stored top), or keep today's full-range hole and fix the fill to delete messages the server did not return? Android wipes them; tdlib does nothing.
- Owner: should the per-chat marker be the dormant RegularChatState (per peer) or one account-level value, and should the stamp be the common pts or a reset generation counter?
- Owner: must the fix cover surfaces the channel scheme also leaves stale (shared media other than music, gallery, search, reply previews, Saved Messages tags), or only history views?
- Owner: should the common reset and fetchChatListHole also raise ChannelState.invalidatedPts when they advance a channel's pts, so channels reached by the reset get their existing validation?
- Owner: acceptable request budget and throttling when every regular chat becomes invalid at once (no cap or backoff exists today for channel validation).

## reset-staleness: What a differenceTooLong account reset (_internal_resetAccountState) leaves stale for regular chats (users, basic groups) and secret chats, how the remaining stored messages are holed and displayed, and what other clients do

I read everything at HEAD 69939c45c0 (`git show HEAD:<path>`) and modified nothing.

**1. What the reset fetches and writes.** `_internal_resetAccountState` (submodules/TelegramCore/Sources/State/ResetState.swift:6-164):
- Fetch: `updates.getState` (L7), then `fetchChatList(.general, limit: 100)` (L10). That is one `messages.getDialogs` with `exclude_pinned` (100 chats, FetchChatList.swift:279-289), plus `messages.getPinnedDialogs(folder 0)` (FetchChatList.swift:273), plus one `getDialogs(folder, limit 32)` for each folder (in practice the archive) the first page references (FetchChatList.swift:311-323).
- Holes: in one transaction, every peer in `ChatListIndexTable` other than a secret chat is set to `.notIncluded` and gets a `.everywhere` Cloud hole over 1...Int32.max-1 (L18-25). That table holds every peer that ever had a top message or an inclusion, and its rows are never deleted (ChatListIndexTable.swift:159-166, 338-340).
  - `.everywhere` also writes the hole into every regular tag space: `MessageHistoryHoleIndexTable.add` at MessageHistoryHoleIndexTable.swift:323-338, with `messageHoles = MessageTags.all` from SyncCore_StandaloneAccountTransaction.swift:6-11. Shared media, pinned, mentions, unseen reactions and poll votes are all covered.
  - The reset adds no thread holes except for forum channels (L27-34), no custom-tag (saved-tag) holes, no Local, Scheduled or QuickReply namespace holes, and no global-tag (Calls) holes.
- Chat list: every chat-list entry and hole is removed except secret chats (L40-41, L89-94). New holes are added: one in the root list at `lowerNonPinnedIndex`, only when the first page was a slice, and a full hole in the archive (L96-99).
- Data stored for fetched dialogs only:

  - non-empty drafts (L44);
  - notification settings (L55);
  - top messages, with `.UpperHistoryBlock` (L56);

  - chat TTL (L60-75);

  - unread mention, reaction and poll-vote counts (L129-137);

- Then it zeroes the Saved Messages tag summaries (L143-149), reindexes the unread counters (L151), and overwrites pts, qts, date and seq from `getState` (L153-158).

**2. Holes around the messages that stay stored, and how the history view treats them.**
- `.UpperHistoryBlock` (Postbox.swift:2204-2219) removes the hole, in every space, from the earliest fetched id of each peer up to Int32.max-1. So each fetched dialog ends with a hole over [1, top-1] and no hole over [top, max]. Every peer that was not fetched keeps the full hole.
- `sampleHoleRanges` (Postbox/Sources/MessageHistoryViewState.swift:655-903) cuts the view off at a hole.
  - If the anchor (for example the first unread message) is inside a hole, the whole window is clipped (L703-704).
  - Otherwise the first gap between loaded messages, walking outward from the anchor, that touches the hole clips everything beyond it. A stored message whose own id lies in the hole is clipped too (L771/L785).
- So after a reset a regular chat shows only its new top message (plus anything stored above it, see §4). Every older stored message is hidden until `ManagedMessageHistoryHoles` fills the hole.

**3. What the fill fixes and what it does not.**
- `storeAndCloseHole` (Holes.swift:1053-1213) calls `addMessages(.Random)` and `removeHole(filledRange)` at L1185.
- For an id that is already stored, `MessageHistoryIndexTable.addMessages` (L99-101) produces `.InsertExistingMessage`, and `MessageHistoryTable` (L353-364) runs `justUpdate(keepLocalTags: true)`. The fresh server copy replaces content, edits, reactions, poll results, the media-read flag and the pinned and mention tags, so every message the server returns is fresh.
- Nothing deletes stored ids inside `filledRange` that the server did not return. If the server returns nothing, `filledRange` is the whole requested range (L1133-1135).
- Result: messages deleted during the gap, including a whole history cleared remotely, are hidden while the hole lasts and come back as soon as the fill closes the range around them. Nothing removes them later.

**4. The "ghost tail".** A message deleted during the gap whose id is above the dialog's new `top_message` is outside every hole, because the hole starts at `top`. It is visible at once and is never removed. It also becomes the chat-list preview and sort key, because `MessageHistoryTable.topIndex` (L753-770) picks the newest stored message with no hole check, and `ChatListTable` (L405-424) uses it. This applies to the top-100 chats at once, and to every other chat when a chat-list hole fill stores its top message with `.UpperHistoryBlock` (Holes.swift:1320).

**5. Stale inventory: the reset fixes some, others heal lazily, the rest stay wrong.**
- Chat list beyond the top 100 / top 32 archived:
  - Those chats are `.notIncluded` until a chat-list hole fill reaches them. That fill also repairs their read state, counters, notification settings and drafts.
  - `managedChatListHoles` walks the whole root and archive lists in the background only when the account has folders (ManagedChatListHoles.swift:47-72, `latestHole`). Otherwise holes are filled only while a chat-list view shows them, that is, on scroll.
  - Until then those chats drop out of the badge and folder counters, because `debugReindexUnreadCounts` counts only included peers (ChatListIndexTable.swift:706-790).
- Stays wrong even for the top 100:
  - Drafts cleared remotely during the gap are kept, because only `.draftMessage` is parsed (FetchChatList.swift:133) and nil is skipped (RestoreFetchedDrafts.swift:97-111).
  - Archive pinning is lost until the archive's top hole is fetched.
- Cached data for users and groups is not cleared; the reset clears it for channels only (L35). Pinned message id, blocked, peer settings, chat theme and group participants refresh on the first chat or profile open in the process, at most once per 5 minutes (AccountViewTracker.swift:1830-1857). That fetch also refreshes per-peer notification settings (UpdateCachedPeerData.swift:293, 540).
- Reactions:
  - Re-polled every 20 s only for visible messages in basic groups and channels (ChatHistoryListNode.swift:3414-3419; AccountViewTracker.swift:851).
  - In 1:1 chats, a reaction changed during the gap on a stored message is fixed only when a fill or another update re-fetches that message.
- Polls: open polls in any visible view are re-polled every 30 s (AccountViewTracker.swift:49-62, 540-596). I found no equivalent refresh for todo lists.
- Global notification settings: fetched only when absent (ManagedGlobalNotificationSettings.swift:57-87), so an `updateNotifySettings` for users, groups or channels during the gap is never recovered.
- Calls tab: it reads global tags and the reset adds no global-tag hole. Calls during the gap are missing, and deleted call messages stay, until their chat is filled.
- Stories: re-polled every 60 s by `StorySubscriptionsContext` (StoryListContext.swift:533-541).
- Scheduled messages: validated by hash whenever the scheduled list is open (HistoryViewStateValidation.swift:379-396, 678-725).
- Contacts: re-synced by `getContacts(hash)`, but behind `.waitForUpdatedState` (ContactSyncManager.swift:181). At HEAD the reset's completion never clears `isUpdating` (Q1; HEAD AccountStateManager.swift:924-934, compare L955-958), so that sync is blocked until relaunch.
- Pinned bar (tag view) and the unread-mention "@" navigation keep stale tags. They show ghost pins and ghost mentions once their tag space is filled, unless the main fill re-fetched those messages. Only the channel validation path strips stale tags (HistoryViewStateValidation.swift:931-1000).
- Secret chats (G10):
  - The reset keeps their chat-list rows and stored history.
  - It overwrites qts from `getState`, so encrypted messages between the old and new qts are never fetched. They come back only if the peer sends again and the seq-gap resend fires (ProcessSecretChatIncomingDecryptedOperations.swift:203-236).
  - An `updateEncryption` lost in the gap is not recovered, except that a chat declined during the gap is detected on the next send through `ENCRYPTION_DECLINED` (ManagedSecretChatOutgoingOperations.swift:2174).

### Design implications

- Two failure shapes need separate answers. Edits are already fixed for every message a fill re-fetches, because the hole clips the old copies until then. What is missing is deletion: (1) ids above the server's top message (the ghost tail), and (2) ids inside a filled range that the server no longer returns. Surfaces that read stored messages by id without a hole check (reply previews, the chat-list preview, the pinned and '@' tag views, the Calls tab) see the stale copies.
- Cheapest fix for the ghost tail, inside the reset: for each fetched dialog with top message N, call transaction.deleteMessagesInRange(peerId, Cloud, N+1, Int32.max-1) (Postbox.swift:150; MessageHistoryTable.swift:495), the equivalent of tdlib's delete_newer_server_messages_at_the_end. Run it before addMessages in the same transaction. It should go through _internal_deleteMessages-style media cleanup. The Local namespace (pending messages) is unaffected.
- Fill-time deletion as an alternative to a per-peer marker: FetchMessageHistoryHoleResult already computes strictFilledIndices (Holes.swift:1131-1180). Deleting, or for tag spaces untagging, stored ids inside the strict range that the server did not return would remove messages deleted during the gap. The caveat: this assumes messages.getHistory/search returns every message in that id span for a user or basic-group peer, which I did not verify against the API docs, and it would change fill semantics for every chat, not only after a reset. A safer variant applies it only to peers marked stale by the reset.
- Full revalidation needs the two primitives regular chats lack. (a) A per-peer staleness marker: today HistoryState is .channel/.scheduledMessages/.quickReplyMessages only, and peerChatState is added to history views for channels only. (b) A per-message version to compare against it: ChannelMessageStateVersionAttribute needs a dialog pts, which users and groups lack, so a reset generation or a timestamp would do. The request and apply shape already exists: validateChannelMessagesBatch is plain messages.getHistory(hash), and validateBatch updates, strips tags or deletes. The deletion check would use messages.getMessages instead of channels.getMessages. Note that validateBatch applies new content only when edit_date changed, so it does not fix reactions or poll results.
- Cost of the Android-style alternative: wipe stored history for every non-encrypted dialog on differenceTooLong and refetch. It is correct by construction but discards the local cache (media references, offline reading) for every chat, including the ones beyond the top 100.
- Keep qts and date: set pts from differenceTooLong.pts (iOS uses getState and ignores it), keep the local qts/date/seq, and call getDifference again. This is what tdlib and Android do. It is the cheapest fix for G10 (encrypted messages in the qts gap) and may also recover the non-pts other_updates since the old date (notify settings, updateEncryption, drafts, user names). That second part rests on server behaviour I did not verify. It is independent of message revalidation and depends on the Q1 cycle fix (the reset must be followed by another pollDifference).
- Gaps any reset must also cover: the reset should drop or refresh cached data for users and groups as it does for channels (pinned id, blocked, peer settings); clear drafts that are empty on the server (handle draftMessageEmpty for fetched dialogs); reset the pinned-tag and other tag summaries it does not set; add a global-tag hole for Calls; and add thread holes for Saved Messages sublists (accountPeerId), plus custom-tag holes if those views need them.
- Counters: the badge and folder counters drop chats beyond the fetched set until the chat-list holes are walked. A correct reset should either walk the whole chat list in the background (as managedChatListHoles already does when folders exist) or keep the old inclusion until replaced.
- Enabling pts_total_limit also requires fixing Q3 (standalonePollDifference still calls preconditionFailure() on differenceTooLong, HEAD AccountStateManager.swift:1437) and Q11 (dialogsNotModified → .never()). The extension already receives differenceTooLong whenever the server decides to send it, so Q3 is independent of the limit.
- Tests can be built on the existing StateSync fixtures: scripted getState/getDialogs/getHistory answers with a stored message above the new top (ghost tail), a stored message inside a filled range that the server omits, an emptied draft, and a qts gap with an encrypted message. Assert the stored state after the reset and after a fill.

### Open questions

- Server: for a user or basic-group peer, does messages.getHistory return every existing message with id inside the span it returns? This decides whether 'not returned' can safely mean 'deleted' at fill time.
- Server: after differenceTooLong, will getDifference with the new pts and the old date/qts return the encrypted messages and the non-pts other_updates (updateNotifySettings, updateEncryption, updateDraftMessage, updateUserName…) since the old date, or are those also too long? tdlib and Android depend on this; I could not verify it.
- Server: how long are encrypted messages retained once a later getDifference acknowledges a higher qts? This decides whether G10 losses are permanent or recoverable by a re-poll.
- Server: what gap size triggers differenceTooLong when pts_total_limit is unset? The docs only say 'pts < latestPts - size'; 'only very large gaps' is the owner's statement.
- Owner: is discarding the local cache (Android's approach) acceptable for a reset, or must stored messages and media be kept and revalidated per chat?
- Owner: should a fix delete messages that a fill no longer returns for all chats, or only for peers marked stale by a reset?
- Not verified: any recovery for an updateEncryption lost during the gap (a secret chat accepted, requested or discarded by the peer). The only path found is ENCRYPTION_DECLINED on the next send (ManagedSecretChatOutgoingOperations.swift:2174).
- Not verified: whether the pinned-message count ('N of M', .pinned tag summary) is ever refreshed for users and groups after a reset.
- Not traced end to end: Saved Messages sublists after a reset (thread hole index untouched), and the 20 s completedEntries suppression in ManagedMessageHistoryHoles (L159-165) when a hole identical to one just completed is re-added (the reset does not call resetPeerHoleManagement).
- Interplay with the concurrent Q1/Q11 work: once the reset finishes its cycle, ContactSyncManager's waitForUpdatedState and AccountTaskManager unblock. That should be re-checked as the repair path for contacts and contact names after a reset.

## server-api: Server API options for revalidating a regular chat's (private chat / basic group) locally stored messages after a common-box gap (differenceTooLong): getHistory hash, getMessages, getPeerDialogs, search, getDifference limits

Bottom line. In private chats and basic groups, deletions and edits made during an unrecoverable common-box gap can be found by range validation. These chats share one account-wide message id sequence that only ever increases (core.telegram.org/api/updates, "Recovering gaps for very old messages": "All messages belonging to private chats and basic groups are stored in one single instance … because they share the same id sequence"). So an id window [lo, hi] that the client has already seen can only lose messages, never gain them. The cheapest correct request per window is the one HistoryViewStateValidation.swift already sends for channels (:560): messages.getHistory(peer, offset_id: hi+1, add_offset: 0, limit: n, max_id: hi+1, min_id: lo-1, hash: H(local run)), where n is the local message count and at most 100 (tdlib MessagesManager.h:1675 MAX_GET_HISTORY = 100, "server-side limit"; iOS cuts runs at 64, HistoryViewStateValidation.swift:89-103). A messagesNotModified answer (swift_scheme.tl:296, `count:int` only) validates the whole run in one tiny round trip. Any other answer is complete for [lo, hi] if it holds fewer than n messages or the same ids. Only an answer of exactly n messages with different ids leaves [lo, min returned id) unverified, which can happen only if the local run had a gap. Edits come from the answer itself. Stored ids missing from the covered window are only candidates: confirm them with messages.getMessages (at most 200 ids per call; ids from every regular chat can go in one call) before deleting. The open question is the server hash: nothing shows the server honors getHistory's `hash` for non-channel peers. iOS sends it only for channels, and tdlib, tdesktop and Android always pass 0. A wrong or unsupported hash fails safe (the full slice comes back), so the hash changes the cost, never correctness.

The hash input is only described as "result IDs (message IDs or other fields with name id, or some extra fields in some cases)", and getHistory "supports all result navigation parameters including message ID hashes". The same page says max_id/min_id are applied after slicing by offset and limit, which is why a short answer means the window is complete. No page gives getHistory's per-message hash fields. Two side notes on that code. iOS hashes quick replies with the scheduled formula (:735, :437-456), which does not match the documented quick-reply formula. Nothing ever noticed, which shows how quietly a hash mismatch degrades to full answers. And iOS sorts by (timestamp, id) while the server presumably orders by id, so chats where dates do not follow ids (imported history, unverified) would never get notModified.

Where iOS uses the hash today. It is sent only under HistoryState `.channel`: getHistory (:560), messages.search for tag views (:554) and getReplies (:634). Hole fills always pass 0 (Holes.swift:619, :876, :958). For channels, a missing id is confirmed through channels.getMessages (:823-866). For every other history state the code treats all missing ids as removed with no confirmation (:864-865). That branch would need a messages.getMessages confirmation before it could be used for regular chats.

What the hash can and cannot see. The common-box pts updates that change a stored message are updateNewMessage, updateDeleteMessages, updateEditMessage, updateReadHistoryInbox and updateReadHistoryOutbox, updateWebPage, updateReadMessagesContents, updatePinnedMessages and updateFolderPeers (swift_scheme.tl:324-406). A hash over id, pin and edit_date-or-date catches only deletions, edits and pin changes. It misses updateReadMessagesContents (media_unread: unplayed voice and video notes, read mentions) and updateWebPage (new link-preview content), because neither changes edit_date. Reactions are not pts events: core.telegram.org/api/reactions tells apps to short-poll visible messages every 15-30 s or call messages.getMessagesReactions, so they are outside the gap problem. A notModified window is therefore correct for existence, edits and pins only. Either accept the media_unread and webpage residue, or send hash 0 on the first pass after a differenceTooLong, which returns full payloads at the cost of a hole fill today.

messages.getMessages. The docs' prescribed tool after a too-long gap: "messages.getMessages for all basic groups and private chats, passing up to 200 IDs … This method is not limited by the common message box size … These methods will return placeholder messageEmpty constructors for deleted or otherwise non-representable messages" (core.telegram.org/api/updates). tdlib agrees: MAX_SLICE_SIZE = 200 "server-side limit", with user and basic-group ids from any chats mixed in one call (MessagesManager.cpp:15187-15212). getMessages has no hash, so every call returns full messages. That makes it right for two jobs. One is confirming deletion candidates. The other is revalidating messages read outside a history view (reply headers, pinned bar, search hits) by id, across chats. It does not suit sweeping whole histories. A messageEmpty may come without peer_id. iOS's Api.Message.id() then returns nil (UpdatesApiUtils.swift:137-143), and StoreMessage returns nil for messageEmpty (StoreMessage_Telegram.swift:1525). So confirmation must work as the channel code does: requested ids minus ids returned as real messages (HistoryViewStateValidation.swift:844-856). tdlib deletes on messageEmpty only for channels, and only for ids at or below the last new message id it held (MessagesManager.cpp:275-287). For ordinary chats tdlib does not delete on messageEmpty at all (:223-235).

Other methods.
- messages.getPeerDialogs (:2655) returns each dialog's top_message, read_inbox_max_id/read_outbox_max_id, unread counts and its top message. On getDifference's pts_total_limit, core.telegram.org/method/updates.getDifference says: "if provided and pts + pts_total_limit < remote pts, updates.differenceTooLong will be returned … If the remote pts is too big (> ~4000000), this field will default to 1000000". Until e543bf1e2e (2024-10-15) iOS sent pts_total_limit = 1000.

Other clients. None revalidates regular-chat messages after differenceTooLong.

That is correct but throws away the cached history.
- No client sets a getHistory hash: tdlib passes 0 (MessagesManager.cpp:597-598, :537, :613; MessageQueryManager.cpp:922-923), tdesktop has `historyHash = uint64(0)` (apiwrap.cpp:3506, history_widget.cpp:5031/5083/5183/5269), and Android has `// req.hash = hash;` commented out (MessagesController.java:11754).

What iOS does after a reset today. _internal_resetAccountState adds a 1…Int32.max-1 hole to every non-secret chat-list peer (ResetState.swift:21-23). The `.everywhere` space also adds holes in every configured tag space (MessageHistoryHoleIndexTable.swift:323-337). Fills refetch with hash 0, and addMessages overwrites a stored message with the same id (MessageHistoryIndexTable.swift:99-101 → InsertExistingMessage → justUpdate, MessageHistoryTable.swift:353-364), so edits to refetched messages are corrected. Readers that bypass history views (transaction.getMessage for reply headers, the pinned bar, local search) see stale content whether or not a hole exists. A smaller existing race: validateBatch replaces a stored message whenever the two edit dates differ, even if the stored one is newer (HistoryViewStateValidation.swift:895-901). A late answer can therefore revert an edit that arrived by update in the meantime.

Conclusion and limits.
- Per window: one getHistory with hash, at most 100 messages, covering only a hole-free local run of one chat. Unchanged costs about 8 bytes (only if the server honors the hash for that peer type); changed costs a full slice.
- Deletion candidates: one messages.getMessages per 200 ids, shared across chats.
- Top of each chat: getPeerDialogs (batched) catches deleted newest messages and read state.
- Deletions in regular chats can be detected from a getHistory range: within the covered window, a stored id that is missing is gone (deleted for everyone, deleted for me, history cleared, or TTL expired), provided it is (a) confirmed via getMessages and (b) not above the newest common-box id held when the request went out.
- Not verified here: server support for the hash on users and basic groups, the exact server hash fields, getPeerDialogs' peer cap and flood budgets. I made no API calls. The sim has no login, and this task was read-only.

### Design implications

- Range validation is sound for regular chats because the common-box id sequence only increases: a seen window [lo, hi] only loses messages. Window rule: with limit n equal to the local count of a hole-free run, the answer covers [lo, hi] if it holds fewer than n messages or the same ids, and covers only [min returned, hi] otherwise. Validate only hole-free local runs.
- Per-window request: getHistory(offset_id: hi+1, add_offset: 0, limit: n ≤ 100, max_id: hi+1, min_id: lo-1, hash: H(run)). This is the shape iOS already sends for channels (HistoryViewStateValidation.swift:560). It costs one round trip per run of up to 100 messages per chat; iOS cuts runs at 64.
- The hash must not carry correctness: whether the server honors it for users and basic groups is unverified, and a mismatch silently returns full slices. If it is not honored, a validation costs the same as today's hole fill (hash 0, full slice).
- An edit-date hash leaves media_unread (updateReadMessagesContents) and link-preview (updateWebPage) changes stale on a notModified window. Either accept that residue, or send hash 0 on the first pass after differenceTooLong.
- Deletion: collect stored Cloud ids that are missing from the covered window, confirm them with messages.getMessages (≤200 ids per call, batched across all regular chats), and delete those not returned as real messages. Never delete on an error answer. Never delete ids above the newest common-box id held when the request was sent (tdlib's last_new_message_id guard).
- Edits: guard every replacement by edit_date, so a late answer cannot revert a newer edit that arrived by update. The current validateBatch replaces whenever the dates differ (HistoryViewStateValidation.swift:895-901).
- Marking unvalidated messages: the common box has one pts, and regular-chat answers carry none, so the channel scheme (invalidatedPts + a per-message ChannelMessageStateVersionAttribute stamped from the answer's pts) becomes one account-wide generation or id watermark set at reset. Messages stored before it need validation. An alternative is the docs' 'known valid ranges' structure: per peer, record the id ranges still unvalidated at reset instead of adding a hole.
- Option A, minimal: keep the reset's holes, and make regular-chat fills (getHistory, plus per-tag messages.search) delete stored ids missing from the strictly covered window (strictFilledIndices is already computed in Holes.swift), with getMessages confirmation. This adds no requests beyond the confirmations. It fixes deleted messages coming back in history views, but not readers that bypass views (reply headers, pinned bar, local search). Those need by-id revalidation through getMessages for messages older than the reset generation.
- Option B, like channels: no hole. Mark the generation and run HistoryViewStateValidation for regular chats with the hash. Cached history stays visible offline. The cost depends on whether the server honors the hash.
- Option C, as Android does: wipe stored messages, media index and holes of non-secret dialogs on differenceTooLong. Simplest correct option, but every cached history is lost on each differenceTooLong; with a 1000-5000 pts_total_limit that happens often.
- A full background sweep with getMessages costs ceil(N/200) requests, each with full payloads, and risks FLOOD_WAIT. No client does one; prefer lazy validation on read or view.
- getPeerDialogs (batched per peer) is the cheap check for the newest end: stored ids above top_message, and at or below the request-time watermark, are deleted. It also refreshes read state and unread counts.
- Tag spaces (shared media and others) get reset holes too. Their validation via messages.search with filter and hash uses the same window rule per tag, but a message missing from a tag window may only have lost the tag. The existing code removes the tag rather than deleting (HistoryViewStateValidation.swift:932-998).
- Once differenceTooLong is handled correctly, sending pts_total_limit (docs recommend 1000-10000; Android sends 1000/5000; iOS sent 1000 until 2024-10-15) trades a long difference download for a reset plus lazy validation. differenceTooLong can already arrive without the flag (default 1,000,000 once remote pts exceeds ~4M).

**What the protocol docs say** (https://core.telegram.org/api/updates, "Recovering gaps for very old messages"):
- The common message box is "usually … 5000000". A getDifference with pts < latestPts − size returns differenceTooLong. Clients "have to handle this by re-fetching the latest state for that message box and re-start fetching updates from that state, and filling any gaps in older messages manually by using … messages.getMessages, if necessary".
- "The common update state can also be fetched from updates.differenceTooLong" (constructor: `pts: The new state to use`).
- The suggested bookkeeping is a list of known gap-free message-id ranges with a `pending` flag. There is ONE such structure for all private chats and basic groups together, because they share one id sequence. An unfillable gap sets `pending`. Gaps are refilled with messages.getMessages, which "will return placeholder messageEmpty constructors for deleted … messages". That gives an explicit deletion signal, which messages.getHistory does not.
- pts_total_limit (https://core.telegram.org/method/updates.getDifference): "if provided and pts + pts_total_limit < remote pts, updates.differenceTooLong will be returned … If the remote pts is too big (> ~4000000), this field will default to 1000000". The updates page recommends "1000-10000" for the common box.

**tdlib.** It never sends pts_total_limit. GetDifferenceQuery sends `updates_getDifference(0, pts, 0, 0, date, qts, 0)` (UpdatesManager.cpp#L192-L202), and the only flagged variants use pts_limit=1/qts_limit=1 (ConfirmPtsQtsQuery L219-L226, GetPtsUpdateQuery L248-L255).

Its differenceTooLong branch (UpdatesManager.cpp#L2182-L2191) does three things and has a `// TODO` in it:
- logs ERROR (only when session_count ≤ 1);
- calls `set_pts(difference->pts_)`, leaving date and qts untouched;
- calls `get_difference(...)` again. This works because on_get_difference clears `running_get_difference_` on entry (L2054-L2060).

Nothing in MessagesManager is touched. Regular dialogs keep `last_new_message_id`, `first/last_database_message_id` and `have_full_history`. History is served from the database ranges as before, and open_dialog only re-polls channels (L17063). So in private chats and basic groups, messages sent, edited or deleted inside the gap are never recovered.

The same holds for tdlib's other common-pts resets: PERSISTENT_TIMESTAMP_INVALID → set_pts(INT_MAX) → getState (L1322-L1336, L1357-L1385) and updatePtsChanged (L4623-L4636). Neither touches the message DB.

Only channels get real gap handling. MessagesManager.cpp#L35012-L35028 is a design comment listing four strategies: (1) delete all messages; (2) keep memory, delete the DB; (3) keep everything but stop treating it as continuous; (4) per-range continuity with lazy getHistory checks. It also warns that outgoing live locations must not be deleted. on_get_channel_dialog (L34980-L35075) then does the following:
- unloads the dialog, or marks it unload-on-close;
- clears first/last_database_message_id, so the DB is no longer served as continuous history;
- clears have_full_history;
- invalidates message indexes;
- in one case wipes the DB via remove_dialog_newer_messages (L12033-L12068).

**Telegram Desktop.** It never sends pts_total_limit: `MTPint(), // pts_total_limit` in Updates::getDifference (api_updates.cpp#L693-L719, L712). It does not support differenceTooLong at all. Updates::differenceDone (L490-L527) only logs `"API Error: updates.differenceTooLong is not supported by Telegram Desktop!"` (L523-L525).

Unlike every other branch (L484, L501, L510), that branch does not call `_ptsWaiter.setRequesting(false)`. The only other place that clears the flag is getDifferenceAfterFail (L663-L670), which runs only after a getDifference *error* (failDifferenceStartTimerFor at L633). While the flag is set:
- getDifference() returns early (L696);
- mtpUpdateReceived applies only group-call updates (L898-L907).

My inference is that common-box update processing stops until relaunch. The impact is small because tdesktop keeps no message history on disk. The storage key enum (storage/storage_account.cpp#L78-L111) has drafts, settings and stickers, but no history. Each launch starts with updates.getState and requestDialogs (L234-L259, L478-L486). For channels, channelDifferenceTooLong (L407-L428) calls `history->setNotLoadedAtBottom()` and `requestChannelRangeDifference`. The second is a forced getChannelDifference with a `channelMessagesFilter` over the loaded id range (L795-L888), and it has no regular-chat counterpart.

**Telegram Android.** It is the only one of the three with a deliberate regular-chat story, and that story is a wipe.

pts_total_limit is sent on the first getDifference after process start or account cleanup: `getDifferenceFirstSync` is true at init (MessagesController.java#L363) and reset in cleanup (L6650). The value is 5000 on Wi‑Fi and 1000 otherwise (L16872-L16880). So differenceTooLong is a routine fast catch-up for Android, not a rare overflow.

On differenceTooLong (L16892-L16898):
- it clears loadedFullUsers and loadedFullChats;
- it calls `resetDialogs(true, lastSeq, res.pts, date, qts)`, using the constructor's pts and the request's own date and qts;
- it calls stories cleanup.

resetDialogs (L12833-L12990) fetches messages.getPinnedDialogs and messages.getDialogs(limit 100, exclude_pinned). It then calls MessagesStorage.resetDialogs (MessagesStorage.java#L4577-L4720), which does the following in one storage-queue job:
- deletes, for every non-encrypted dialog id in its `dialogs` table: chat_pinned_count, chat_pinned_v2, dialogs, **messages_v2**, bot_keyboard(_topics), media_v4, messages_holes and media_holes_v2, plus all of polls_v2 (L4625-L4636);
- re-inserts the fetched dialogs with their top messages. putDialogsInternal calls `createFirstHoles` (L17496, L17264-L17288), which makes everything below each top message a hole;
- saves seq/pts/date/qts via `saveDiffParamsInternal` (L4665);
- resets the dialog-load offsets.

Only after that does completeDialogsReset (L12992-L13075) clear `gettingDifference`, persist pts/date/qts, call getDifference() from the new pts, clear and reload drafts, and rebuild the in-memory dialog list.

Channel tooLong uses the same policy for one peer: overwriteChannel (MessagesStorage.java#L11404) deletes the channel's messages, holes, media and topics and re-seeds from the dialog.

Things I read but did not confirm at runtime:
- The DELETE has no mid/send_state filter, so unsent local rows would go too. I did not trace what happens to them.
- If either dialogs request fails, `resetDialogs(false, …)` is never called, and both `resetingDialogs` and `gettingDifference` stay true. That is a wedge similar to our Q1.
- An open ChatActivity only gets `dialogsNeedReload`. I did not check its in-memory messages.

In normal operation Android trusts its cache. processLoadedMessages (L11911-L12030) goes to the server only when the cache read returned nothing (`resCount == 0 …`). When it does, the getHistory hash it sends covers abs(peer id), message id, pinned and edit_date-or-date (L11989-L12008).

**Synthesis.** The two clients that act on differenceTooLong agree on state handling:
- take pts from the constructor, not from getState;
- keep the local qts and date (tdlib changes only pts; Android passes the request's date/qts into saveDiffParamsInternal);
- resume getDifference immediately.

They differ only on the message store: Android drops all non-secret history, and tdlib drops nothing (TODO). tdesktop does not handle the case and gets away with it because it has no disk cache.

None of the three revalidates regular-chat messages in place. The only in-place revalidation designs are tdlib's channel comment, tdesktop's channel range-difference, and the docs' shared range structure with getMessages/messageEmpty.

By contrast, the iOS reset calls getState and overwrites pts/qts/date/seq (audit §6.3; G10). That is exactly what both clients avoid.

**iOS facts that bear on the design** (read at HEAD, not run):
1. Re-adding a message whose id already exists replaces it: MessageHistoryIndexTable.swift:96-105 emits `.InsertExistingMessage`, and MessageHistoryTable.swift:353-364 calls `justUpdate(keepLocalTags: true)`. So any hole fill that re-fetches a message fixes its edits.
2. A hole fill never deletes stored messages missing from the response. Holes.swift:1075-1180 computes `strictFilledIndices` and :1185 only removes the hole. The resulting `strictRemovedIndices` is used only for thread anchoring (ReplyThreadHistory.swift:985).
3. `ChannelMessageStateVersionAttribute` is written only on channel paths (ApplyUpdateMessage.swift:367, FetchChatList.swift:182, Holes.swift:1037, HistoryViewStateValidation.swift).

Given the full `1...Int32.max-1` hole the reset adds to every chat-list peer (ResetState.swift), once that reset completes the dominant staleness should be messages deleted during the gap, plus edits in ranges no view ever re-fills. That is my inference; I did not test it. It slightly narrows the owner's statement that edits stay stale.

### Design implications

- State handling (no conflict between the clients here): take pts from the differenceTooLong constructor, keep the local qts and date, and resume getDifference immediately. tdlib and Android both do this and neither calls getState. On iOS that would replace the getState call in _internal_resetAccountState, fix G10 (secret-chat messages in the window are then delivered by the next getDifference, which runs from the old qts), and give Q1 the follow-up poll it is missing.
- Ordering to copy from Android: fetch the dialogs first; then, in one storage transaction, rebuild the store and write the new pts/date/qts; only after that clear the 'getting difference' state and request getDifference again. If the process dies mid-reset, the next launch retries from the old pts, gets differenceTooLong again, and redoes the reset safely. Do not copy Android's failure path: a failed getDialogs leaves it wedged. iOS's retryRequest already avoids that.
- Option A, Android-style wipe. For every non-secret peer, remove stored Cloud-namespace messages and their tag summaries in the reset transaction (the full hole is already added). Keep the Local namespace (unsent), scheduled messages, quick replies and secret chats. tdlib's warning also applies: outgoing live locations and pending edits/reactions (PendingMessageActions) must survive. Cost: offline history disappears, everything is downloaded again, and the already 'very large' reset transaction gets bigger. Coverage gap: chatListGetAllPeerIds only covers chat-list peers, while Android's DELETE covers every row in its dialogs table. Peers that have stored messages but no chat-list entry need their own enumeration.
- Option B, tdlib-channel/docs-style invalidation of the common box. Store a single invalidated-common-pts marker (by analogy with ChannelState.invalidatedPts). It can be one value for all regular chats because private chats and basic groups share one message-id sequence, which is why the docs prescribe a single range structure. Tag every stored regular-chat message with the common pts it was stored at (a common-box counterpart of ChannelMessageStateVersionAttribute, which today is written only on channel paths). Messages below the marker, or with no tag, are validated when viewed: getHistory(hash) answers messagesNotModified when nothing changed; otherwise reconcile, using messages.getMessages, where messageEmpty means deleted. This keeps offline history and makes a low pts_total_limit cheap. Cost: an extra attribute on every regular-chat store, validation traffic for each viewed page, and a dependence on the server's history hash covering edit_date for non-channel peers (see the open questions).
- Option C, strict-range reconciliation in the hole fill (the smallest change). The reset already puts a 1...Int32.max-1 hole on every chat-list peer, and Postbox already overwrites re-fetched ids, so edits are repaired in any range a view fills. What is missing is deletion: messages of that peer stored inside the strict filled range (Holes.swift strictFilledIndices) but absent from the response are left behind. Deleting them is valid for regular chats, because a getHistory page of consecutive messages for one peer omits only messages that no longer exist for this user. Caveats:
- races with updates arriving during the request (tdlib re-issues the request in that case, MessagesManager.cpp L7262-L7268);
- the server may return fewer messages if deletions race;
- surfaces that read messages without filling that range (search, shared media, reply previews, pinned list, notifications, Saved Messages sublists) stay stale until they are filled;
- it should apply only to ranges the reset invalidated, or be shown correct for every fill, because it changes how every chat history fill behaves.
- The right pts_total_limit depends on which option is chosen. With A, every differenceTooLong means a full re-download. Android accepts that by sending 1000 or 5000 only on the first sync after launch, which makes the wipe a routine fast catch-up. With B or C a differenceTooLong is cheap, so the docs' 1000-10000 range applies. Leaving the parameter out does not avoid the path for large accounts: the server applies 1,000,000 when the remote pts is above about 4M, and the common box size is about 5M.
- None of the three clients has a counterpart to the notification extension. Whatever replaces the Q3 trap is a new decision. One option: the extension stops on differenceTooLong and leaves pts untouched, so the app performs the reset.
- Regression tests should pin these properties:
- the persisted pts equals the pts in differenceTooLong;
- qts and date are unchanged after the reset;
- getDifference is requested again after the reset;
- for whichever store option is chosen, a message deleted in the gap is not shown after the next fill or validation, and a message edited in the gap shows the new text.

### Open questions

- Server: does messages.getHistory's `hash` for user and basic-group peers include edit_date, the pinned flag and the peer id, and what is the exact formula? Android hashes abs(peerId), id, pinned and edit_date-or-date for every peer type (MessagesController.java L11989-L12008). iOS's channel validator omits the peer id. Option B depends on getting messagesNotModified exactly when nothing changed.
- Server: what exactly is the pts in updates.differenceTooLong: the current remote pts, or the oldest pts still in the box? And what does getDifference(pts = that value, old date, old qts) return? Both tdlib and Android rely on qts and date being independent of the overflow; it is not documented whether events between the two values are skipped.

- Owner: keep offline history in regular chats after a reset (options B or C, closer to tdlib's thinking and the docs), or accept Android's wipe and re-download (option A, simplest and already used in production by Android)?
- Owner: which surfaces must be correct right after a reset: chat history only, or also search, shared media, the pinned list, Saved Messages sublists and notifications? This decides whether reconciling in the hole fill (option C) is enough.

1. The client can already receive differenceTooLong without sending a limit. Correct handling is needed whatever limit is chosen. The method page (https://core.telegram.org/method/updates.getDifference) says of pts_total_limit: "If the remote pts is too big (> ~4000000), this field will default to 1000000". The updates guide (https://core.telegram.org/api/updates, section "Recovering gaps for very old messages") says the common message box "is usually very large ... 5000000 for the common message box", and that a pts below (latestPts - size) "will return an updates.channelDifferenceTooLong/updates.differenceTooLong constructor". So today's "unlimited" client is capped at a gap of about 1M pts on accounts whose pts is above about 4M, and at the box size on every account. When that happens:

2. The documentation contradicts itself on what pts_total_limit means.
   - The method page: "For fast updating: if provided and pts + pts_total_limit < remote pts, updates.differenceTooLong will be returned. Simply tells the server to not return the difference if it is bigger than pts_total_limit". That makes it a reset threshold on the gap remaining at each request.
   - The updates guide: "clients can specify the number of updates to be returned by each call during pagination using the pts_total_limit parameter ... It is recommended to use a limit equal to 10-100 for channels and 1000-10000 otherwise", and the limit "does not limit the total number of updates". That makes it a per-call page size.

   Two pieces of evidence favour the method page:
   - tdlib caps a single response with `pts_limit` (flags.1), not `pts_total_limit`. `ConfirmPtsQtsQuery::send` (UpdatesManager.cpp:220-226) and `GetPtsUpdateQuery::send` (:249-255) send `PTS_LIMIT_MASK` with pts_limit = 1, and `on_get_pts_update` (:2203-2271) expects a slice holding exactly one update.
   - iOS shipped pts_total_limit = 1000 for about 20 months (below). The owner's Q14 reason assumes resets followed in practice.

   My conclusion: pts_total_limit is the differenceTooLong threshold; pts_limit is the per-response cap, but nobody has shown that values above 1 are honoured. The "1000-10000" figure belongs to the page-size reading and is not advice on a reset threshold. No public source (docs, tdlib, tdesktop, Android) gives the server's default slice size. The differenceTooLong constructor page says "the specified state must be used to refetch updates" (pts: "The new state to use.").

   Android is correct by wiping: it cannot show stale messages, and keeping the old qts and date makes the next getDifference fetch the secret-chat backlog. iOS keeps the messages and only adds full holes (R:19-36), which is the Q14 problem.

5. What an unlimited difference costs the main app (read from the code, not measured). Each slice runs the following in sequence:
   - one getDifference;
   - a snapshot transaction (`initialStateWithDifference`);
   - interpretation, after a hop onto the process-wide MTContext queue (G7);
   - channel resets for each `updateChannelTooLong`: asynchronous here, one getPeerDialogs per channel, merged after the chain ends;
   - a sequential resolve chain: forum threads; `resolveAssociatedMessages`, one messages.getMessages/channels.getMessages per peer with missing reply targets (SyncResolve.swift:744-858); unknown emoji files; forum threads again; stories; missing chat infos;
   - one replay write transaction holding the Postbox queue (M:878-904).

   That is 1 to about 6 sequential round trips per slice. Beyond the per-slice work:
   - The continuation is put back at index 0 after the head is popped (M:945-946 with `addOperation` .first, M:587-606). The chain therefore holds the operation queue until it ends; pushed updates and RPC results queue behind it.
   - Events are merged with `currentEvents.union` (M:939) and delivered once at the end. `addedIncomingMessageIds` (and `addedReactionEvents`, which hold full Message objects) grow with the whole gap. `processEvents` then runs `messagesForNotification` for every id in one transaction (M:1192-1200), while the in-app consumer uses only `messageList.last` (TelegramUI/Sources/ApplicationContext.swift:326).
   - `isUpdating` is true for the whole chain (M:789, cleared at M:957). That shows "Updating…" (Account.swift:1407-1432), and AccountTaskManager waits for the first false (AccountTaskManager.swift:51-59).

   Chain time ≈ (gap / S) × T, where S is pts per slice and T is seconds per slice; neither is known. As a hypothetical with S = 1000 and T = 1 s: a 100k-pts gap is about 100 slices (~1.7 min), and the 1M cap about 17 min. Every factor of 10 smaller in S is 10 times longer.

6. In the notification extension, the same pipeline runs with `asyncResetChannels: nil`, so channel resets are one inline getPeerDialogs, and events are dropped. `restartIfError` restarts the pipeline after each slice (NSE:2050-2059) under `pollTimeout = min(15.0, remaining)` (NSE:1537-1541, 2068; the connection deadline is 25 s after start). Each slice commits pts, so partial progress survives between pushes, but a stale account burns up to 15 s of CPU and network on every non-channel push. That matches the 2026-07 CPU-burn reports. Peak memory per slice is the parsed slice plus its replay. The extension's memory ceiling of about 24 MB is forum- and DTS-reported (developer.apple.com/forums/thread/64634, seen through search only), not Apple documentation. The extension cannot shrink a slice today: `ptsLimit: nil` at M:1420.

7. Values, assuming a reset that revalidates (or wipes) regular chats lands first. The owner's constraint and fix-plan Step 6b forbid any limit before that.
   - Main app: send pts_total_limit so that the worst-case chain stays within a tolerable "Updating…" time B: L_app ≈ B × S / T. Anchors: Android 1000/5000; iOS's 1000, which made the reset path common; the server's own implicit 1,000,000. My provisional starting point is low tens of thousands of pts (e.g. 20k-50k). It should come from app config, and it rests on measuring pts per slice and wall time per slice first.
   - The trade-off: a lower limit means shorter, lighter chains and less starvation of the queue, but more resets. Each reset invalidates every chat's history (full holes, refetched when opened). It restores read states, pins, drafts, notification settings and mention/reaction counts for the top 100 dialogs only. It loses every other state change that `other_updates` carried in the gap, unless that state has its own refresh path.
   - Extension: it must never reset (owner), so a limit only means "answer differenceTooLong cheaply and leave it to the app", which matches the planned Q3 fix ("done, nothing written"). Keep L_nse ≤ L_app: backlog work the app will discard by resetting is wasted. Size it to about one or two 15 s budgets, and use pts_limit as the memory guard if the server honours it. The cost is payload-only notifications until the app opens, and the extension stops shrinking a backlog above L_nse.

### Design implications

- Correct differenceTooLong handling is required whatever limit is chosen. The server already answers differenceTooLong for gaps above about 1M pts on accounts with pts above about 4M, and for anything older than the 5M common box. Today the main app runs a reset with Q1/Q11/Q14/G10, and the extension traps (Q3). The limit only sets how often the path fires.
- Every pts_total_limit value below depends on the revalidating (or wiping) reset landing first. The owner's constraint and fix-plan Step 6b forbid sending any limit before then.
- Model the corrected reset on tdlib and Android for state: adopt differenceTooLong.pts, keep the stored qts and date, and run getDifference again after the reset. This closes G10 (secret-chat and date-based backlog) with no extra request type. Overwriting from getState (ResetState.swift:153-158) is strictly worse.
- A reset loses more than stale messages. It restores read states, pins, drafts, notification settings and mention/reaction counts only for the top 100 dialogs, and it drops every other_updates-carried change in the gap (sticker sets, folders, privacy, notify settings, contacts, etc.) unless that state has its own refresh. Correct handling should trigger those refreshes, or the cost of each reset should be accepted.
- Android's model is correct by wiping: it deletes the stored messages of every non-secret dialog, so nothing stale survives. If iOS revalidation of regular chats turns out too hard, wiping or invalidating regular-chat history (keeping media in MediaBox) is the known-good fallback. Its cost is losing the offline cache.
- Main app: choose L_app ≈ B × S / T (B = tolerable 'Updating…' time, S = pts per slice, T = seconds per slice). S and T are unmeasured. Provisional starting point: low tens of thousands of pts (e.g. 20k-50k), much larger than the 1000 that shipped in 2023-24 and made resets routine, and far below the server's implicit 1M. Deliver it through app config (precedent: ios_disable_parallel_channel_reset_v2 at M:803-807) so it can be tuned or switched off without a release.
- Prerequisite measurement: log, per slice, the pts delta (intermediate_state.pts - request pts), the new_messages/other_updates counts and the wall time. Log the total gap once the chain ends (final state pts - starting pts). Without these, any limit value is a guess.
- Sending the limit on the first poll after launch only (Android) or on every poll is an owner decision. With a correct reset, every poll is more consistent, because the gap size does not depend on how fresh the process is. Android's way limits resets to cold starts. The server checks the limit on every request that carries it, so a continuation request can in principle get differenceTooLong after earlier slices were committed. The reset must then complete the cycle and deliver the carried events (the Q1 fix).
- Unlimited chains have costs that a limit does not fix. Consider these independently: the continuation at index 0 holds the operation queue for the whole chain; events from the whole gap are merged in memory and materialized in one processEvents transaction, where only messageList.last is used; isUpdating holds 'Updating…' and AccountTaskManager for the whole chain. Bounding the notification materialization (e.g. only the last N ids, or only ids newer than the in-app notification window) is cheap and safe.
- Extension: it must never reset (owner). There, a pts_total_limit means 'answer differenceTooLong in one cheap round trip and leave the backlog to the app', matching the planned Q3 fix (done, nothing written). Keep L_nse ≤ L_app, because backlog work the app will discard by resetting is wasted. Size it to roughly one or two 15 s budgets of slices. Trade-off: no more 15 s of CPU and network per push on stale accounts (the 2026-07 burn reports), against payload-only notifications until the app opens and an extension that stops shrinking a backlog above L_nse. An extension differenceTooLong must never be taken to mean the app should reset.
- pts_limit (flags.1) is a second knob, separate from the reset threshold. It could bound per-slice memory and transaction size, which matters most under the extension's reported ~24 MB ceiling. tdlib shows the server honours pts_limit = 1; whether larger values cap a slice is unverified, so confirm before relying on it. It needs no schema change: ptsLimit is already a parameter, passed as nil at M:834 and M:1420.
- A limit counts pts, and pts is only a proxy for work. Read receipts are cheap; messages with reply targets, custom emoji, stories or new peers each add resolve round trips. Expect T per slice to vary widely by account.
