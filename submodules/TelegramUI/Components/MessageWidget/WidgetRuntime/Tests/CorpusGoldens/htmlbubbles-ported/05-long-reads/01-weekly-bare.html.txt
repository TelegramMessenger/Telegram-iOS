      <h2 id="h2" hidden=""></h2>

      <section class="sec" data-sec="0" data-min="1" data-title="A tiny web page">
    <p><span class="drop">E</span>very message in this app is a tiny web page. Not a web <i>view</i> — there is no browser process, no web engine and no network stack hiding behind the bubbles. Instead each message is handed to <b>litehtml</b>, a compact C++ library that understands HTML and CSS well enough to lay out documents, and then asks its host application to do the actual drawing. That split — <i>litehtml decides where things go, you decide how they look on screen</i> — is what makes it such a good fit for chat.</p>
    <p>This article walks through the whole journey of a message: from a string of HTML to pixels on a Retina display. Along the way we will look at what litehtml does for you, what it deliberately leaves out, and the handful of decisions that make HTML bubbles feel native instead of embedded.</p>
      </section>

      <section class="sec" data-sec="1" data-min="1.5" data-title="Parsing: from bytes to a tree" hidden="">
    <p>litehtml does not ship its own HTML tokenizer. It bundles <b>gumbo</b>, Google's HTML5-compliant parser, which means malformed markup is repaired exactly the way a browser would repair it: unclosed paragraphs are closed, stray <code>&lt;/b&gt;</code> tags are ignored, and a <code>&lt;div&gt;</code> inside a <code>&lt;p&gt;</code> splits the paragraph in two. That matters in a chat app, where messages come from people (and bots) who do not run validators.</p>
    <p>The gumbo tree is then converted into litehtml's own element classes — <code>el_div</code>, <code>el_text</code>, <code>el_image</code>, <code>el_table</code> and friends. Text is split into words and spaces at this stage, because the layout engine wraps text one word at a time. Every word is measured once by calling back into the host: <code>text_width("hello", font)</code>.</p>

      </section>

      <section class="sec" data-sec="2" data-min="1.5" data-title="Styling: the cascade, minus the drama" hidden="">
    <p>Three stylesheets are applied to every bubble, in order. First the <b>master CSS</b> that ships with litehtml — the equivalent of a browser's user-agent stylesheet, which knows that <code>&lt;b&gt;</code> is bold and <code>&lt;ul&gt;</code> has bullets. Then our <b>user CSS</b>, generated per bubble: it sets the system font, the text colour for light or dark mode, link colours, code blocks, and the small utility kit (<code>.card</code>, <code>.btn</code>, <code>.badge</code>…) used by the cards in this demo. Finally the message's own <code>&lt;style&gt;</code> blocks and inline <code>style</code> attributes.</p>
    <p>Selectors cover what you would expect in practice: descendant and child combinators, classes and IDs, attribute selectors, <code>:first-child</code>, <code>:nth-child(even)</code>, <code>:not()</code>, <code>:hover</code> and <code>:active</code>, plus <code>::before</code> and <code>::after</code> with generated content and CSS counters. Hover over the rows of the table in the next section to see <code>:hover</code> at work.</p>
    <div class="pull">“litehtml decides where things go; you decide how they look on screen. That split is the whole trick.”<small class="muted">— the one sentence to remember from this article</small></div>
      </section>

      <section class="sec" data-sec="3" data-min="1.5" data-title="Layout: boxes all the way down" hidden="">
    <p>After styling, litehtml builds a <b>render tree</b> of <code>render_block</code>, <code>render_inline</code>, <code>render_table</code> and <code>render_flex</code> items. Layout is a single call: <code>document::render(maxWidth)</code>. It positions every box, wraps every line, resolves percentages, floats and absolutely-positioned children, and returns the document's <i>natural</i> width — how wide it would like to be if nothing forced it to wrap.</p>
    <p>That return value is exactly what a chat bubble needs. We render once at the maximum bubble width; if the natural width is smaller, we render again at that width and the bubble shrinks to hug its text. Because word widths were measured during parsing, re-layout is pure arithmetic and typically takes a small fraction of a millisecond.</p>

      <section class="sec" data-sec="4" data-min="1.5" data-title="Painting: the container contract" hidden="">
    <p>litehtml never touches a pixel. To draw, it walks the render tree and calls methods on a <b>document container</b> — an abstract C++ class the host implements. There are about thirty of them, and they read like a to-do list for a 2D renderer:</p>
<pre><code><span style="color: #af52de">class</span> <span style="color: #007aff">document_container</span> {
  <span style="color: #8e8e93">// text</span>
  uint_ptr <span style="color: #ff9500">create_font</span>(descr, doc, metrics);
  pixel_t  <span style="color: #ff9500">text_width</span>(text, font);
  <span style="color: #af52de">void</span>     <span style="color: #ff9500">draw_text</span>(hdc, text, font, color, pos);
  <span style="color: #8e8e93">// boxes</span>
  <span style="color: #af52de">void</span>     <span style="color: #ff9500">draw_borders</span>(hdc, borders, pos, root);
  <span style="color: #af52de">void</span>     <span style="color: #ff9500">draw_solid_fill</span>(hdc, layer, color);
  <span style="color: #af52de">void</span>     <span style="color: #ff9500">draw_image</span>(hdc, layer, url, base_url);
  <span style="color: #af52de">void</span>     <span style="color: #ff9500">set_clip</span>(pos, radius);
  <span style="color: #8e8e93">// … ~20 more: gradients, list markers, links</span>
};</code></pre>
    <p>Our implementation (<code>LHContainer.mm</code>) maps these onto Apple's APIs. Text goes through <b>CoreText</b>: every word becomes a <code>CTLine</code>, which gives us kerning, ligatures and — crucially — automatic font fallback, so emoji 🎉, Cyrillic, Japanese and Arabic all render even though the CSS asked for the system font. Shapes, borders and gradients are <b>CoreGraphics</b> paths; conic gradients map directly onto <code>CGContextDrawConicGradient</code>.</p>
    <div class="note"><b>Note.</b> The same container renders to an on-screen <code>NSView</code> and to an off-screen bitmap. The <code>lhrender</code> command-line tool in this repo uses the bitmap path to turn any HTML file into a PNG — handy for testing messages without launching the app.</div>
      </section>

      <section class="sec" data-sec="5" data-min="1" data-title="Fitting text into bubbles" hidden="">
    <p>The hardest part of the integration is not drawing, it is <i>agreeing</i>. litehtml asks for a font's ascent, descent, height and x-height, and then trusts those numbers when it stacks lines. If the container measures a word one way and draws it another, lines overlap or wrap one word too early. The fix is boring and strict: measure and draw with the identical <code>CTLine</code>, round the line height up once, and derive the descent from it so that <code>ascent + descent</code> is exactly the height litehtml thinks it is.</p>
    <p>Images follow the same rule. litehtml asks for an image's size <i>during layout</i>, so the container must know it synchronously. In this MVP that means images come from <code>data:</code> URIs, SF Symbols (<code>sf:heart.fill</code>) or pictures the app draws at launch (<code>app:aurora</code>). Remote images would need an asynchronous load followed by a re-layout of the affected bubble — very doable, just not done yet.</p>
    <div class="warn"><b>Watch out.</b> litehtml has no <code>overflow-wrap</code>. A 200-character URL without spaces will overflow its bubble; the bubble clips it. If you generate HTML from user text, insert <code>&lt;wbr&gt;</code> or zero-width spaces into very long tokens.</div>
      </section>

      <section class="sec" data-sec="6" data-min="1" data-title="What's missing — and why that's fine" hidden="">
    <p>There is no CSS grid, no <code>box-shadow</code>, no <code>opacity</code>, no transforms and no CSS animations. There is no bidirectional text reordering, so Hebrew and Arabic words are shaped correctly but placed left-to-right. And litehtml itself never runs a line of JavaScript — which for a messaging app is a feature, not a bug: the layout engine cannot track you, mine cryptocurrency or rewrite the chat around it.</p>
    <p>Interactivity lives next to the engine instead. A message may carry a script that runs in its own JavaScriptCore sandbox, with no network and a strict CPU budget. Its <code>render()</code> returns a fresh HTML string, litehtml lays it out again, and clicks on <code>data-action</code> elements call back into <code>onAction</code> — which is how this article turns pages, resizes its text and remembers what you have read.</p>
    <div class="tip"><b>Try it.</b> Right-click this article and choose <i>View HTML Source</i>. It is one message: a <code>&lt;style&gt;</code> block, a two-line static fallback and a script whose <code>render()</code> returns only the section you are reading.</div>
