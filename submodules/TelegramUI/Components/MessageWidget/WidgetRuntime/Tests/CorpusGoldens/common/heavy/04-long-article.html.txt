  <h1>One widget, three renderers: what a fair comparison needs</h1>
  <div class="meta"><div class="av"></div><div><div class="bold" style="font-size: 13px">Leo Marin</div><div class="tiny muted">10 October 2026 · 6 min read</div></div></div>
  <p class="lead">A system web view, a Rust layout engine and a C++ one all draw the same card. The numbers they produce are only comparable when the card is one they all draw the same way.</p>
  <h2>The problem with the old corpora</h2>
  <p>Our generated corpus was written for a browser. Seventeen of its forty widgets use <code>display: grid</code>, several draw their charts with inline SVG, one flips a flashcard with a 3D transform, and almost all of them lean on <code>box-shadow</code> for depth. Loading those files on litehtml or Blitz gives a time, but not a comparable one: an engine that skips the SVG does less work, an engine that collapses the grid into a column does more, and neither picture is what the user would see.</p>
  <p>The Telegram demos are closer, since they were written against litehtml in the first place, but they also depend on a host stylesheet, an action prelude and a handful of image schemes that mean nothing outside that app.</p>
  <div class="quote">A benchmark where one contestant quietly skips half the course is not a benchmark.<span>From the review of the first Blitz numbers</span></div>
  <h2>What the common profile keeps</h2>
  <p>The intersection is larger than it sounds. Every engine in the comparison lays out <b>block and inline</b> content, <b>flexbox</b> with wrapping and growth, <b>tables</b> with collapsed borders, lists, borders with radii, solid and gradient backgrounds, <code>var()</code> custom properties, <code>overflow: hidden</code>, and relative or absolute positioning. The theme switches through a media query, which the validator rewrites for every renderer.</p>
  <h3>Kept out on purpose</h3>
  <ul>
    <li><b>Grid</b>, because litehtml has none; every grid in this corpus is a wrapping flex row or a table.</li>
    <li><b>Inline SVG and canvas</b>; charts are bars made of divs, icons are letters in coloured circles.</li>
    <li><b>Transforms, shadows, opacity, transitions and keyframes</b>; motion is JavaScript writing widths and text at 60 Hz, which is also the honest way to measure update cost.</li>
    <li><b>Form controls</b>; neither native engine draws a value or a slider, so buttons are styled spans and toggles are two-state chips.</li>
    <li><b>Emoji and symbol fonts</b>; Blitz on iOS and the web build fall back to tofu, so the text is ASCII plus a few punctuation marks every font carries.</li>
    <li><b>Floats, counters, pseudo-element content, <code>gap</code>, <code>calc()</code>, <code>text-overflow</code></b>; some are missing on one side, some are untested, none is worth the risk.</li>
  </ul>
  <h2>What the files exercise</h2>
  <p>Four groups, each aimed at a different cost. The <b>cards</b> are static layouts of realistic density: a profile, a receipt, a timetable, a dashboard. The <b>interactive</b> files change state on a tap: a tab swap, a poll bar growing, a calendar rebuilt from a string. The <b>live</b> files keep going without input: a clock at 1 Hz, bars filling with <code>requestAnimationFrame</code>, a ticker at 2 Hz, a log appending lines. The <b>heavy</b> files are the ones that make a layout engine sweat: a 60-row table, 300 chips, a deep tree, this article.</p>
  <ol>
    <li>Start-up: from host creation to the first frame with content.</li>
    <li>A text-only update: the clock, the counters, the ticker.</li>
    <li>A structural update: a rebuilt list, a swapped panel, an appended log line.</li>
    <li>A full relayout under load: sorting the long table, expanding the whole tree.</li>
  </ol>
  <p>For litehtml every update is the fourth kind, because the engine rebuilds the document from a string; that is the real cost of its model and the corpus should make it visible rather than hide it.</p>
